# Decisions

Choices made where the implementation plan left things open. Newest at the bottom.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-11-03 | **React 19** for the UI (the plan allowed plain TS or light React). | Team preference; chips, toolbar, quiz banner and walkthrough player are UI-state heavy. |
| 2026-11-03 | **Plain Three.js inside React**, not React Three Fiber. The scene lives in an imperative `SceneController` class (`frontend/src/viewer/controller.ts`) mounted by a thin `<Viewer>` component. | The plan's action executor calls controller methods directly (`highlight`, `isolate`, `focus`…). Keeping Three.js out of React's render cycle makes that straightforward and avoids one more dependency. |
| 2026-11-03 | **Vite 8 + TypeScript 7**, created by hand rather than `npm create vite`. | Same layout as the official `react-ts` template, minus ESLint for now. |
| 2026-11-03 | **One `.env` at the repo root**, shared by backend (`pydantic-settings`) and frontend (`envDir: '..'`). | One place to configure; Vite only exposes `VITE_*` variables, so secrets stay server-side. |
| 2026-11-03 | **venv + pinned `requirements.txt` / `requirements-dev.txt`** for Python. | Works on every machine with no extra tools; `uv` can replace it later without code changes. |
| 2026-11-03 | **`httpx2`** for the FastAPI test client. | Starlette deprecates `httpx` in the test client. |
| 2026-11-03 | **Ports:** frontend 5173, backend 8000. | Tool defaults. |
| 2026-11-03 | **No Docker or Kubernetes for now.** Add a single backend Dockerfile only if we deploy. | Local-first project with a laptop live demo; containers add setup cost without benefit until deployment. |
| 2026-11-08 | **21 registry structures from the 40 GLB meshes** (`assets/structures.json`). A structure lists every mesh it covers, e.g. `aortic_valve` → 3 leaflets, `pulmonary_veins` → 4 veins. Papillary muscles and cardiac veins are one structure each. | Students talk about structures, not leaflets or branches; grouping keeps the quiz and reference resolution at that level. Splitting a group later only adds IDs. |
| 2026-11-08 | **Interventricular septum and myocardium left out of the registry.** | Neither is a separate mesh in Z-Anatomy (see `docs/asset_prep.md`). Add them back if the septum is split out in Blender. |
| 2026-11-08 | **Neighbor links are two-way**, and structures may carry an optional `notes` field for model caveats. | Two-way links make retrieval expansion predictable and are easy to check; `notes` keeps known gaps (missing leaflets, partial vessels) next to the entry they affect. |
| 2026-11-08 | **`resolved_refs` is a list of `{word, start, structure_ids}`**, not the plan's word → ID map. | A map can't hold "compare this and this": both words are the key "this". `start` (character offset) lets the UI link each word to its chip. |
| 2026-11-08 | **Stub `POST /api/command`** returns sample responses from `assets/fixtures/` until the agent exists. | The frontend can integrate against the real endpoint and format now; the fixtures double as frontend mock data and are checked against the schema by the tests. |
| 2026-11-10 | **Selection lives in a small store outside React** (`frontend/src/selection/store.ts`); components read it with `useSelection`. | The scene controller and, later, the action executor change the selection without going through React. |
| 2026-11-10 | **A plain click on empty space clears the selection**; a Shift-click on empty space does nothing. Esc also clears. | Matches common 3D and file-manager behavior, and a missed Shift-click shouldn't wipe a multi-selection. |
| 2026-11-10 | **The click log only holds clicks for structures that are still selected.** Removing a structure (Shift-click or chip ×) drops its click; a plain click restarts the log. | `click_events` and `selection` in the request always describe the same set, so reference resolution never sees a click for something the student deselected. |
| 2026-11-10 | **Viewer colors are set in the frontend** (`viewer/colors.ts`) by registry `group`, with red for oxygen-rich and blue for oxygen-poor vessels. All meshes of a structure share one material. | The GLB's exported materials are mostly grey. One material per structure makes it highlight as a unit. |
| 2026-11-10 | **Selected structures turn gold**; hover shows a name tooltip. | Gold stays readable on both the red and the blue vessels. The tooltip will need an off switch for quiz mode, where it would give away the answer. |
| 2026-11-10 | **A hovered structure gets slightly bigger** and keeps its own color: about 5–6% larger around its middle, and thin structures also swell outward so vessels look thicker (`HOVER_GROWTH` in `viewer/controller.ts`). | Tried and dropped: a glow (too subtle, changed the color) and fading the other structures (the team didn't like the look). |
| 2026-11-10 | **The hover growth is drawn in the shader**, not by scaling the meshes, and the coronary vessels are drawn slightly closer to the camera while another structure is grown. | Picking keeps using the real geometry, so a grown chamber can't block the cursor from the vessels on it. Without the depth lift, a grown chamber swallowed those vessels. |
| 2026-11-10 | **Leader-line labels** name every structure that can currently be seen, in two columns beside the heart, with a "Labels" switch (on by default). Built as an HTML/SVG overlay in `viewer/labels.ts`, not Three.js' `CSS2DRenderer`. | The plan's `CSS2DRenderer` puts text on top of the structure, which covers small structures. Columns with lines keep the model clear and let labels be spaced so they never overlap. |
| 2026-11-10 | **A structure is labeled only while a point on it is visible**, tested by casting rays from the camera to a few sample points on its surface. | Otherwise labels would point at structures hidden inside or behind others. Hiding a layer makes the labels behind it appear without extra code. |
| 2026-11-10 | **Labels are clickable**: hovering one acts like hovering its structure, and clicking selects it (Shift adds). | Gives a second way to select small structures that are hard to click. Like the tooltip, labels must be off in quiz mode. |
| 2026-11-10 | **`three-mesh-bvh`** speeds up ray casting (a search tree per mesh). | Without it one ray tested all ~300k triangles: the label visibility check took ~260 ms and made rotation stutter. With it the check takes ~2.5 ms, and picking is faster too. |
| 2026-11-10 | **Structures panel** (`ui/StructurePanel.tsx`): the four layers with their structures nested under them, and an eye button on each row and each layer. It replaces the plan's row of layer buttons. | Several structures sit inside others (valves, papillary muscles), so students need to hide single structures, not only whole layers. |
| 2026-11-10 | **Hidden structures live in a store outside React** (`visibility/store.ts`), like the selection. `SceneController.setVisibility` writes to it. | The panel and the agent's `set_visibility` action then always agree, whichever one made the change. |
| 2026-11-10 | **The panel is a sidebar that the 3D view sits beside**, not an overlay on top of it. | The heart and its label columns re-center in the remaining space instead of being covered. |
| 2026-11-10 | **"Recenter" only moves the camera** (`SceneController.resetView`): back to the anterior view over 0.6 s, orbiting the heart. It leaves the selection and hidden structures alone. | The button was asked for as a way back to the starting position. The agent's `reset_view` action can call the same method; whether that action should also clear highlights and show everything is still open. |
| 2026-11-10 | **`Viewer` exposes a small handle** (`ViewerHandle`, via `ref`) for commands from the rest of the app. | The Recenter button lives in `App`; the action executor will need the same route to the controller. |
| 2026-11-10 | **Vitest** for frontend unit tests (`npm test`), used for pure logic such as the selection store. UI behavior stays on the manual checklist. | Selection order decides what "here" and "there" mean, so it is worth an automated check; Vitest reuses the Vite config. |
| 2026-11-14 | **First topic for study sessions: the heart's coronary arteries.** The radial nerve and humerus become the second topic. | The viewer and backend already work on the heart, so a full session loop is reachable sooner. Proposed by Hanna on the frontend side; not yet reviewed by both of us, and `docs/user_stories.md` still names the radial nerve first. |
| 2026-11-14 | **Session data is generated from Z-Anatomy, not written by hand** (`backend/scripts/export_region.py`). Structure names, grouping, centre lines and articles all come from the atlas; the only hand-written input is `region.json`, a list of atlas object names. | A hand-written list is per-topic work, which the generality check rules out, and it can drift from the model. |
| 2026-11-14 | **The generated files sit beside the old ones** (`assets/regions/heart/`), and `assets/structures.json` and `heart.glb` stay until both of us agree to switch. | The backend, its tests and `/api/command` read the old registry. |
| 2026-11-14 | **Structure ids are the atlas' names** in lower case with underscores (`anterior_interventricular_artery`). Valves are groups of leaflets, not single structures: 41 structures against the old 21. | Ids then need no lookup table and stay stable when the export is re-run. Our own short ids (`aortic_valve`) had no source in the atlas. |
| 2026-11-14 | **A centre line is a set of pieces**, one per curve in the atlas, each with points, a radius per point, and `attach`: the piece it branches off, how far along, and the gap. Positions on a vessel are therefore "piece + distance along it". | It is exactly what the atlas stores, so nothing is inferred. The pulse, the damage slider and click grading all need a distance along a path and what lies downstream. |
| 2026-11-14 | **A branch joins the path it starts on (within 1 mm), or failing that the vessel whose wall it starts on.** Arteries and veins are never joined to each other. Pieces that only share a starting point are siblings. | Matches how the atlas draws branches: exact shared points inside a vessel, and a start on the wall where a small vessel leaves a large one (the coronaries on the aorta). Veins run beside arteries closely enough to be mistaken for branches otherwise. |
| 2026-11-14 | **All 3,821 atlas articles are exported once** into `assets/text/z_anatomy_articles.jsonl` (10 MB), with the source link each one carries. | They are stored inside the 300 MB Blender file, which the backend cannot open per request. Exporting every region at once means no text step when a region is added. |
| 2026-11-14 | **Heart landmarks are exported but marked as not touching** (`distance_to_surface`). | In the atlas they are floating labels 6 to 44 mm from the heart. Dropping them would lose the names; using them as places would be wrong. |
| 2026-11-14 | **The viewer loads the generated region** (`assets/regions/heart/`): `registry.ts` reads the generated `structures.json`, and a mesh's name is its structure id. The old `heart.glb` and hand-written registry are no longer used by the frontend. | One source of names and ids. The frontend does not call `/api/command` yet, so nothing breaks; the backend still validates against the old registry until both sides switch. |
| 2026-11-14 | **The structures panel is grouped by the atlas' own groups**, with the region's group first and a branch indented under the vessel it comes off. It replaces our four layers. | The layers were ours, not the atlas'. Grouping by the nearest atlas group needs no per-region list. |
| 2026-11-14 | **Size and color are worked out, not listed.** A structure's hover growth comes from its shape (a vessel's radius, a surface's length); its color comes from the nearest atlas group that has one (`viewer/colors.ts`). A surface inside another surface (a papillary muscle) is drawn darker. | `size_class` and `group` were hand-written fields. The color table by group is the one piece of styling still written by us. |
| 2026-11-14 | **A click keeps its exact place** (`ClickEvent.place`): the point in the model's frame (metres) and, on a vessel, the piece of its centre line and the distance along. | Grading by place needs more than which structure was clicked. The wire format for sending it is still to be agreed in the session format. |
| 2026-11-14 | **A place on a vessel is found by distance from the tube's surface, not from its centre line** (`centerlines.ts`, `nearest`). | A point at the base of a thin branch lies inside the thick trunk it leaves, so plain distance gives it to the trunk. Tube surfaces sit exactly one radius from their own piece, which separates the two. |
| 2026-11-14 | **Vessels are painted per vertex** (`SceneController.paint`): each vertex of a vessel knows its piece and distance along, and carries a color and strength that the shader mixes in. The lookup is built the first time a vessel is painted. | Any set of stretches can be painted on any number of branches without changing geometry or materials, and it is fast enough to redraw every frame for a pulse or a slider. Building the lookup for every vessel at load would slow startup for vessels that are never painted. |
| 2026-11-14 | **"Beyond a place" means away from the trunk**: the rest of the piece and every branch leaving after it, in this vessel or another (`Centerlines.beyond`). | For an artery this is what a blockage cuts off. For a vein the blood flows the other way, so the session code must not read it as "downstream" there. |
| 2026-11-14 | **Session format proposed** (`docs/session_format.md`, version `lumen.session/0.1`), with types and a check in `frontend/src/session/format.ts` and a hand-written sample in `assets/fixtures/sessions/`. A proposal until both of us agree. | The player and the agent can be built apart if both aim at one written shape. The sample lets the player be built with no backend. |
| 2026-11-14 | **Parts are sent one at a time**, not as one file. A recorded session (the sample) is the same parts stored in a list. | The agent builds the next part while the student works, and replans after each answer. One file could not change mid-session. |
| 2026-11-14 | **The browser grades a click and tells the backend the result.** The correct region travels to the browser with the case. | The browser already holds the centre lines and the click place, so feedback is instant and needs no round trip. A student could find the answer in the page; acceptable for a study tool. |
| 2026-11-14 | **A camera view names what to look at and from which side**, not camera coordinates. | The agent cannot know coordinates; the viewer can work them out and can check the result is visible. |
| 2026-11-14 | **A source can be `model`**, for a fact measured on the 3D model, beside `notes`, `atlas` and `web`. A case story has no source because it is invented. | Lengths and "the first branch leaves at 47 mm" come from the model, not from any text. Labelling an invented patient with a source would be false. |
| 2026-11-14 | **The format check lists every problem with its path, and checks ids and distances against the loaded model.** It does not check that articles exist or that the anatomy is right. | The agent will produce this JSON; a precise list of what is wrong is what lets it, or us, fix a bad session. The articles file is too large to load in the browser. |
| 2026-11-14 | **The session player is a store plus a stage.** `session/player.ts` holds which part is on screen, the slider position and the answers, with no 3D code. `session/stage.ts` follows it and drives the viewer. The panel (`ui/SessionPanel.tsx`) reads the same store. | Same pattern as the selection: state outside React, so the 3D view and the panel cannot disagree. The store can be tested without a browser, and the backend can later feed it parts one at a time. |
| 2026-11-14 | **A session borrows the viewer and gives it back.** What it hides, tints and paints is kept apart from what the student has hidden or selected, and is undone when the part changes or the session closes. | The student's own view should survive a session. Paint is in named layers so a moving pulse or slider repaints only its own. |
| 2026-11-14 | **A part's clicks are taken before selection** (`SceneController.onPlaceClick`): an answer to a case, or a new place for the slider. Other clicks select as usual. | A case answer should not also turn a structure gold and open a chip. |
| 2026-11-14 | **Names are hidden while a case waits for a click** (labels and the hover name), and return once it is answered. | The case asks for a place found by reasoning; labels would turn it into reading. This is the player's rule, not a field in the format. |
| 2026-11-14 | **A wrong click gets specific feedback where the case foresaw it, and "Show me the answer" appears after the first try.** The case stays open until it is answered or shown. | Matches the format's near misses. Whether to step in after a wrong answer is the agent's decision in the real loop; the player only needs a way out. |
| 2026-11-14 | **The camera for a part is chosen by the viewer**: it frames the named structures from the named side, or, with no side given, from the side where ray tests see the most of them. | The agent cannot know coordinates. A fixed side can still hide the subject, so see the next row. |
| 2026-11-14 | **The sample's views were fixed after testing them.** The case's answer and the slider's first third were hidden in the front view; the parts now look from the left with the pulmonary trunk, left atrium and cardiac veins hidden. A part's `hide` may name a group as well as a structure. | Nothing in the format guarantees that what a part talks about can be seen. Recorded as an open question in `docs/session_format.md`: the agent's check will need a visibility test. |
| 2026-11-14 | **A session hides structures through the visibility store, and resets the heart when it ends.** What a part hides shows in the Structures panel like anything else, and the student can bring it back. At the summary, or when the session is closed, everything is shown and the camera returns to the starting view. This replaces the earlier rule that a session's hiding was kept apart from the student's. | Asked for after trying the player: hidden structures with no sign of it in the panel were confusing, and the heart was left in the last part's view. The cost is that anything the student had hidden before the session is shown again afterwards. |
| 2026-11-14 | **Layout redesign: rail, model, thread.** A narrow rail on the left holds "New session" and the history. The 3D view is the largest area. The session moved to a column on the right and became a thread: the request as a message, the plan, each part as a card (earlier parts collapse to one line), Back and Next, and an input box. The Structures sidebar became a button that opens a compact list over the model. | Asked for after trying the player: the structures list took too much room and the session needed more. A session is already a conversation, so the chat and the session share one column and the student reads in one place. Point-and-ask and the start of a real session both need the input box. |
| 2026-11-14 | **The border between the 3D view and the thread can be dragged**, between 320 px and 60% of the window, with double-click to reset and arrow keys when focused. The width and the rail's open or closed state are kept in the browser. The camera re-aims at the current part when the drag ends. | Asked for. How much room the text needs varies by part and by screen. The viewer already redraws on any size change, so only the re-aim was new. |
| 2026-11-14 | **History is kept in the browser** (`session/history.ts`, `localStorage`): each play-through is saved as it goes and can be reopened where it was left. Entries that no longer fit the session format are dropped on load. | Sessions live only in memory on the backend so far. This is enough to design and demo the rail; once the backend stores sessions the list should come from there. |
| 2026-11-14 | **The input box only starts the sample for now**, and says so. It is disabled during a session. | The tutor is not connected (steps 5 and 7). A box that pretended to answer what was typed would mislead. |
| 2026-11-14 | **Session requests built on the backend as a placeholder** (`backend/app/sessions.py`, `session_schemas.py`): start, next part, answers, finish, and a read-only view of what is held. Every session is the sample, sent part by part. Built by Hanna on the frontend branch as a proposal for the backend owner to review. | It is the seam the agent plugs into: step 7 replaces "send the sample" with "ask the agent" and the browser does not change. Sessions are in memory only. |
| 2026-11-14 | **The format is defined twice, and one file keeps the two in step.** The backend has Pydantic models, the frontend has TypeScript types and its own check, and both test suites load the same sample session; the backend test also requires the sample to come back from the models unchanged. | Two languages need two definitions. A shared file that both must accept is the cheapest way to notice when one side changes alone. |
| 2026-11-14 | **Notes are sent as base64 inside JSON**, not as a multipart file upload. | No new backend package is needed, it matches how the existing request already carries audio, and the Claude API takes a PDF in the same form. The cost is a body about a third larger. |
| 2026-11-14 | **The backend checks shape; the browser checks the model.** A part with an unknown structure or a distance off its vessel passes the backend and is refused by the browser, which shows why and offers to try again. | Only the browser has the model loaded. When the agent arrives it will need the same check before sending, so the region files will have to be loaded on the backend too (step 6). |
| 2026-11-14 | **A session from the backend is fetched as the student goes** (`session/live.ts`): the first part with the plan, each later part on "Next", the summary at the end. Answers are sent as they are given. The player keeps all the state; `live.ts` only decides when to ask. | The agent builds the next part while the student works and replans after an answer, so nothing can be fetched ahead. Keeping the state in one store means a recorded session and a live one play through the same code. |
| 2026-11-14 | **If the backend can't be reached, the app says so and offers the sample held in the app.** | A demo should survive the backend being down. The header says which of the two is playing. |
| 2026-11-14 | **The backend can now answer questions about the model** (`backend/app/region.py`, `measure.py`): what a structure is, where each branch leaves a vessel, what lies beyond a place, the route between two places, and what is in the way of seeing something. Plain functions with no AI, reading the same exported files as the viewer. | The agent must not guess a distance or assume its answer can be seen. In step 4 those were found by hand; these functions return the same numbers. Built by Hanna on the frontend branch as a proposal for the backend owner. |
| 2026-11-14 | **Visibility is worked out by casting rays through the shapes on the backend**, with the `trimesh` library (plus `numpy` and `rtree`), not from a table made at export time and not by asking the browser. | Chosen by Hanna with the whole body in mind. A table grows with the body, is fixed to six directions and answers only one question; asking the browser fails with no browser open, which the evaluation with simulated students needs. A geometry library also serves the later needle path, slice and "what is under here". The cost is three new packages and about three seconds the first time a region's shapes are used. |
| 2026-11-14 | **A sight line starts where the viewer's camera would stand** for the part's view (the same sides, framing and margin as `SceneController.frame`), and a point counts as covered when the line meets another structure before reaching the point's own surface. | The question the agent needs answered is "can the student see this when the part opens". Parallel rays from a side would differ from what the perspective camera shows. |
| 2026-11-14 | **`what_hides` reports, per side: the share visible now, what is in front, and what else to hide to see all of it.** It does not choose. | Whether to hide a chamber or look from another side is a teaching decision, so it is the agent's. Hiding everything on the list is guaranteed to show the target; a test checks that. |
| 2026-11-14 | **Article search is plain word matching over passages** (`backend/app/articles.py`): rarer words count for more, words in the title count for more, at most one passage per article, and articles linked to the region in hand are ranked higher. No embeddings and no index. | About 3,700 articles score in a fraction of a second. It finds "Left anterior descending artery" for a question about that artery even though the model names it differently. It will miss a passage that uses none of the question's words; the agent can ask again in other words. |
| 2026-11-14 | **The backend checks a session's references and its sources** (`backend/app/session_check.py`), with the same messages and paths as the browser's check. | So the agent can be told exactly what to fix before a part is sent. Checking that an atlas source names a real article with its own link is only possible here. |
| 2026-11-14 | **The session agent is built** (`backend/app/agent.py`, `agent_tools.py`, `llm.py`): Claude plans a session, builds each part with lookup tools, and hands each piece of work in through a tool. Built by Hanna on the frontend branch as a proposal for the backend owner. | This is the headline of the product. It replaces "send the sample" behind the requests from step 5, so the browser did not change. |
| 2026-11-14 | **Claude decides; plain code checks.** A part is accepted only if it fits the format, refers to real structures and pieces, has acceptable evidence for every statement, and shows its subject in its opening view. A part that fails is sent back with the field and the reason, up to four times, then left out of the session. | The agent can be wrong in ways that are cheap to catch. Telling it exactly what failed lets it repair its own work. Leaving a part out is better than showing a wrong one. |
| 2026-11-14 | **Evidence, not sources, is what the agent hands in.** For an atlas statement it gives the article and a quote, and code confirms the quote is in the article word for word and fills in the link. For a notes statement it gives the number of a fact; the page comes from the API's citations. For a measurement it says "model". | An agent asked for a link can invent one. A quote can be checked. This enforces "every claim backed by a passage" without a second model. It does not prove the statement means what the quote means. |
| 2026-11-14 | **Notes are read once, with citations.** The PDF goes to Claude with citations on, and the reply is turned into numbered facts, each with the page and the exact text the API says it rests on. The agent then cites facts by number. | The backend has no PDF reader, so it cannot check a quote against the notes itself. The API's citations give a page and text that are not the model's own claim. |
| 2026-11-14 | **Visibility is a gate, with a threshold per kind of part**: 90% of a case's answer, 60% of a slider's track, half of a pulse's route, 30% of a demonstration's highlighted structures. | A case that cannot be answered is worse than a demonstration that is partly covered. The numbers are first guesses. |
| 2026-11-14 | **Replanning happens once per case, and only after a wrong click.** When the student moves on from a case they got wrong at least once, the agent sees their clicks and either carries on or puts one extra part before the rest. A case answered right first time costs no request. | The thinnest replan that still changes the session because of what the student did. |
| 2026-11-14 | **The next part is built on a background thread while the student works on the current one**, and the summary's sources are collected by code from the parts that were sent. | The first part is the only long wait. A list of sources is bookkeeping, not judgement. |
| 2026-11-14 | **The agent is off by default** (`SESSION_SOURCE=sample`). Switching it on is a line in `.env`. Tests replay scripted replies and never call Claude. | With a key in `.env`, every session started in the app would otherwise cost money, including ones started by accident. |
| 2026-11-14 | **Model `claude-opus-5-5` at effort `high`, with the API's default fallback on a declined request**, all changeable in `.env`. Tool calls are not forced, because this model rejects forced tool choice; the agent is told which tool finishes the work and is reminded if it does not call it. | The reference's default model and its advice for agentic work. Not yet run against the real API. |
| 2026-11-14 | **Two real runs of the agent** on "Prepare me on the blood supply of the heart", no notes, from the command line (`scripts/try_agent.py`). Both built four parts that passed every check and play in the viewer. Run 1: 37 requests, 4.5 minutes, about $2. After it, the agent was told to write millimetres for the student, to hide less, and to keep the scope notes short, and the conversation was cached between turns. Run 2: 35 requests, 4.5 minutes, about $1.20, with no metres or ids in the text and no ventricle hidden. | The first proof that the requests are accepted by the API and that Claude can build sessions the checks accept. Still unproven: reading a PDF of notes, the agent adding a part after a wrong click (both runs chose to carry on, the case being the last part), and a session started from the app. A part's title is now taken from the plan, because run 2 renamed one. |
| 2026-11-14 | **A guard stops tests from calling Claude** (`backend/tests/conftest.py`): every test is forced onto the sample, and any real request fails the test. | A routine test run started real sessions for about five minutes, because `.env` had `SESSION_SOURCE=agent` and the tests read it. Tests must not depend on a developer's own settings, least of all one that spends money. |
| 2026-11-14 | **Ray casts take turns** (a lock in `Shapes.crossed`, `backend/app/region.py`), and the shapes are loaded under a lock too. | The search tree behind `trimesh`'s ray casts is not safe to use from two threads at once. Parts are built on background threads, so two builds asking what hides something at the same moment killed the backend process outright. In the app that looked like "the backend can't be reached". A test now casts from eight threads at once. |
